# Syllable render state

> how syllabic karaoke highlight actually reaches the video (syllables field + render precedence)

Syllable-precise karaoke render is wired through a **`syllables`** field, not `highlight_segments`:

- `s05_analyze.py` projects s04 phoneme timings into per-word `syllables` (vowel-nucleus grouping) written to `analysis.json` words[] plus `syllable_map.json` / `syllable_alignment.json`.
- `review_wizard/highlight_velocity.build_word_highlight_segments` chooses segments by precedence: explicit `word["highlight_segments"]` → derived `word["syllables"]` → ≥1.2s vowel-split fallback → single segment. `s06_generate_ass` renders one `\kf` per returned segment.
- So a **manual boundary edit writes `highlight_segments`** (an explicit override that wins over derived `syllables`); s05 keeps emitting `syllables`. Rerun s06/s07 only (NOT s05) so the manual edit survives.
- Invalidation is inherent: rewriting `analysis.json` breaks its manifest hash in `server._artifact_graph_valid` → export blocked until s06/s07 regenerate.

**Syllable review editor (syncsong-style, 2026-07-10):** `GET /job/<id>/review/syllables` renders `templates/syllable_editor.html` (+ `static/syllable_editor.js`) — a per-syllable boundary editor. Backend: `GET …/review/syllables/pending` (worst-confidence-first queue of words with a below-threshold syllable and no manual override), `GET …/audio/vocals` (streamed with range), `GET …/audio/vocals/peaks?start&end&buckets` (server computes waveform min/max so the browser never decodes the whole stem — decoding a 50MB wav client-side hangs the renderer). Editing saves via the existing `POST …/review/syllables/boundary` (writes `highlight_segments` source=manual conf=1.0, deletes output.ass/mp4+manifests to force s06/s07 re-render). Linked from the review page's AUDIO TIMELINE header. Note: the in-app browser screenshot tool times out on the canvas page, but read_page + network + a real save round-trip verify it.

Confidence is per-syllable and (as of 2026-07-10) **source-aware** via `scripts/syllables.py`: `hubertfa` high, `ctc_forced*` low (below the 0.6 uncertain threshold by design → flags `syllable_uncertain` issues), whisper/interpolated lowest. Config lives in `pipeline.toml [syllables]`. See [karaoke-worktree-gitignored-source](karaoke-worktree-gitignored-source.md).

**The actual blocker to syllables is upstream, not this code:** s04 only emits phonemes when HubertFA runs, and HubertFA is *skipped* whenever ONNX exposes only `CPUExecutionProvider` (no GPU/DirectML) — the machine's onnxruntime is CPU-only, so real jobs came out `ctc_forced` with `phonemes:[]` → word-level highlight only. Two things were needed (both landed 2026-07-10): (1) `matplotlib` in the env — HubertFA's vendored `tools/plot.py` imports it at load or s04 aborts; (2) run HubertFA on CPU via `--allow-cpu-hubertfa`, now a config toggle `align.allow_cpu_hubertfa` (`pipeline.toml`, default false, set true here) wired through `pipeline_runner`. With it on, HubertFA runs ~40s/song on CPU and words become `ctc_forced+hubertfa` with real phonemes → 311/354 words render multi-syllable. Better long-term: install `onnxruntime-directml` (AMD box) so an accelerated provider exists.

**P3 done (2026-07-10):** the phoneme duplication was in `_parse_textgrid` (s04) — HubertFA writes a `words` tier and a `phones` tier (see `vendor/HubertFA/tools/export_tool.py`), but the parser tagged every interval with the *first* tier name and returned both tiers mixed. Now each interval is tagged with its real tier (position-ordered scan) and `_phone_intervals()` keeps only the phones tier. Verified: duplicate phoneme intervals 309 words→0.

**Fast-rap over-segmentation + plausibility gate (2026-07-10):** in fast rap, CTC word spans are ~60ms and diverge from HubertFA phoneme positions, so positional assignment (P1) bleeds neighbours' phonemes into a word — "Wolf" (1 vowel) got 5 syllable groups, rendered as 5 fake `\kf`, and the measured-timing confidence branch trusted them (0.8, never flagged) → the empty review queue was *hiding* it. Fix: `syllables.syllabification_is_plausible(text, group_count, word_span_s, min_segment_ms)` — reject the split when phone-group count exceeds the word's orthographic vowel-run count, or the span can't hold that many syllables at the floor. Used in both `split_word_syllables` and s05 `_project_word_syllables`; rejected words render as ONE whole-word highlight (correct for fast words — you cannot show per-syllable timing on a 60ms word). Net on Inner Beast: syllable segments 499→236, rap words (Wolf/red/lights) now 1 highlight each, 20 genuinely-multisyllable words (clawing→cla/wing, beneath→be/neath) still split. Tests: `tests/test_syllable_gate.py`. Honest ceiling: fast rap is word-level only, not syllabic.

**P4 done (2026-07-10):** `basic_text_syllables` now splits by maximal-onset with a digraph/cluster set (`_ONSET_UNITS`) instead of "break after every vowel": `breathing`→`brea/thing`, `hungry`→`hun/gry`. Caveat: HubertFA runs with `--language en`; on non-English lyrics (the Icelandic verses) the English phoneme model invents extra vowel nuclei, so those words over-segment (`Forfeður`→F/or/fe/ð/ur). That is a g2p-language issue upstream, not the splitter — fix by aligning non-English sections with the right language.

**P1 done (2026-07-10):** `_ctc_forced_with_phonemes` (s04) now assigns each phoneme to the word whose [start,end] span contains its midpoint (nearest word on a gap), replacing the old count-ratio distribution — so intra-word timing is real. A word that captures no phoneme stays plain `ctc_forced` with `phonemes:[]` (renders as one highlight). With this, `SOURCE_BASE_CONFIDENCE["ctc_forced+hubertfa"]` was raised to 0.85 (was 0.55). Measured on Inner Beast: median syllable confidence went 0.49→0.763, flagged share 100%→5%. Residual imperfection: CTC word spans vs HubertFA phoneme positions don't always overlap, so some 2-syllable words (e.g. "beneath") capture one phoneme and render as a single high-confidence segment.
